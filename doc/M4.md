Verification results for the open questions

1. Direct-vs-indirect group semantics (pinned): LocalUserGroupManager.GetUserGroupsAsync (line 315) uses WinNT://./{user},user + Invoke("Groups") = direct local-group membership only → NetUserGetLocalGroups with flags = 0 (not LG_INCLUDE_INDIRECT), level 0.
2. password_expired set path (pinned via Microsoft Learn, USER_INFO_4/NetUserSetInfo docs): there is no 10xx info level for it. Correct path = NetUserGetInfo level 4 → set usri4_password_expired (nonzero = must change at next logon, zero clears; usri4_password comes back NULL and NULL means "unchanged"; usri4_user_id ignored; usri4_primary_group_id round-trips) → NetUserSetInfo level 4. Docs guidance "use the specific level per element" → flags via 1008, full name via 1011, description via 1007, password via 1003; level-4 RMW only for password_expired.
3. CsWin32 ADSI projection availability (CONFIRMED): CsWin32 0.3.298 pins Win32Metadata 70.0.11-preview (nuspec). Binary inspection of Windows.Win32.winmd confirms exact names present: ADsOpenObject, ADsGetObject, IADs, IADsContainer, IADsPropertyList, IADsPropertyEntry, IADsDeleteOps, IDirectorySearch, ADS_SEARCHPREF_INFO, ADS_SEARCH_COLUMN, FreeADsMem (namespace Windows.Win32.Networking.ActiveDirectory). The CsWin32-projection approach (M2's proven IWbem pattern: marshal-free function-pointer-vtable structs, vtable order from metadata) is viable — no typelib dump needed. Note: IADs* are dual interfaces, but under allowMarshaling:false CsWin32 emits the full vtable (3 IUnknown + 4 IDispatch + members) from metadata as a struct — the in-house [GeneratedComInterface] IDispatch base is NOT needed (that base is only for source-gen interfaces, not CsWin32 structs).
4. PDH surface (CONFIRMED in same winmd): PdhOpenQueryW, PdhCloseQuery, PdhAddCounterW, PdhAddEnglishCounterW, PdhRemoveCounter, PdhCollectQueryData, PdhGetFormattedCounterValue, PdhEnumObjectsW, PdhEnumObjectItemsW, PdhMakeCounterPathW, PdhValidatePathW, PDH_FMT_COUNTERVALUE all present. PDH_FMT_COUNTERVALUE is a blittable union (CStatus + double/longlong/…) — safe under allowMarshaling:false.
5. NetAPI32 surface (CONFIRMED in same winmd): NetUserEnum/Add/Del, NetLocalGroupEnum/Add/Del/SetInfo/GetMembers/AddMembers/DelMembers, NetUserGetLocalGroups, USER_INFO_4, USER_INFO_1008, LOCALGROUP_INFO_1, LOCALGROUP_MEMBERS_INFO_1/3 all present.
6. Variant bridging technique (CONFIRMED): WbemObject.cs casts the in-house blittable Variant directly to CsWin32's VARIANT* ((VARIANT*)&variant) — the ADSI wrapper reuses this exactly.
7. Error contract (CONFIRMED): AdminService.IsPermissionError (Infrastructure\Admin\AdminService.cs:43) recognizes Win32Exception.NativeErrorCode == 5 and the "Access is denied" message pattern; LocalUsersGroupsPage.xaml.cs (lines 46-49, 110-113) routes through it. throw new Win32Exception((int)status) preserves the contract.

Phase 2 — PerfMon → PDH

Files:

Decision — PDH query topology: per-counter query (one PDH_HQUERY + one PDH_HCOUNTER per cache entry). Justification: (a) exact semantic parity — PerformanceCounter.NextValue() samples per counter on demand, and the VM calls ReadCounterValue per counter in a loop each 1s tick with no tick boundary visible to the service; a shared query would need a "collected this tick" protocol that doesn't exist in the current contract and couples the service to the VM's timer. (b) Fault isolation — one dead counter (vanished instance) rebuilds alone, matching the existing per-counter InvalidOperationException rebuild. (c) Trivial disposal — PdhCloseQuery releases both handles per entry. Cost: N PdhCollectQueryData calls/tick for the observed N ≤ ~tens — negligible at 1 Hz; note the shared-query optimization in a comment as future work.

Mapping: GetCategoriesAsync → PdhEnumObjectsW (MULTI_SZ walk, PERF_DETAIL_WIZARD, refresh=true); Description = "" — documented behavior change: PDH has no CategoryHelp/CounterHelp equivalent for enumeration (optional later: PdhGetCounterInfoW explain text — do NOT do it per-category, too expensive); IsMultiInstance = PdhEnumObjectItemsW instance list non-empty. GetCountersAsync/GetInstancesAsync/GetFirstInstance (keep _Total preference)/CategoryRequiresInstance → PdhEnumObjectItemsW. Counter creation → PdhMakeCounterPathW (PDH_COUNTER_PATH_ELEMENTS, szMachineName = @"\\name" when MachineName != ".") then PdhAddCounterW first, falling back to PdhAddEnglishCounterW on PDH_CSTATUS_NO_OBJECT/NO_COUNTER — user-picked localized names resolve directly; the hardcoded English GetCommonCounters names resolve via the English fallback, which fixes the existing latent bug on non-English OSes. Prime with one PdhCollectQueryData (ignore failure — parity with "initial read may fail"). ReadCounterValue → PdhCollectQueryData + PdhGetFormattedCounterValue(PDH_FMT_DOUBLE) → (float); any PDH failure → close/rebuild once → retry → _lastValues fallback (contract preserved: semaphore, ConcurrentDictionary keyed MachineName\Category\Counter\Instance, float, fallback-to-last-value all stay). RemoveCounter/DisposeAllCounters/Dispose → PdhCloseQuery per entry. SearchCountersAsync → enumeration APIs, same 50-result/5-instance limits, no disposal needed (enumeration creates no counters). .pmcfg save/load and the whole chart/View/VM pipeline: untouched.

Verification: Debug: PerfMon page shows live default-counter values matching Task Manager magnitudes; add a counter via the picker (localized enumeration path); multi-instance auto-fill (_Total); remove counter; save + reload .pmcfg; kill an instance-backed counter's process to exercise the rebuild path.
